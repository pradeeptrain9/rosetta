# Feedback on Nebius Token Factory and NVIDIA Nemotron

Written from building Rosetta, a COBOL-to-Python migration tool that proves
behavioural equivalence by differential execution. Everything below was
observed, not assumed.

## Nebius Token Factory

**What worked well**

- The OpenAI-compatible surface meant the official `openai` SDK worked unchanged,
  including `files.create(purpose="fine-tune")` and `fine_tuning.jobs`. Routing
  work between model tiers became a string swap rather than a client rewrite,
  which is what made it cheap to measure "should the cheap tier do this job?"
- `GET /v1/models` being available is the single most useful thing for a project
  with a long life. We discover each tier by matching served ids against ordered
  patterns and cache the result, so the project keeps working as ids rotate
  instead of breaking on a hard-coded string.

**Friction, in rough order of how much time it cost**

1. **Stale base URL in circulation.** We first built against
   `https://api.studio.nebius.com/v1`, which now 307-redirects to the Token
   Factory docs. The working endpoint is
   `https://api.tokenfactory.nebius.com/v1`. A redirect that carried the API
   through, or an error body naming the new host, would have saved an hour.
   Worth sweeping older tutorials and cookbook entries for the old hostname.

2. **No Nemotron model is fine-tunable, and that is hard to discover.** Our whole
   distillation design assumed we could fine-tune Nemotron Nano on repair traces
   generated by Ultra. The fine-tunable catalog is Llama, Qwen, Gemma, DeepSeek
   and gpt-oss. This is a defensible product decision, but the two catalogs —
   served models and fine-tunable models — live in different places, so the
   constraint only surfaces when a job is rejected. **Suggestion:** expose a
   `fine_tunable: true/false` flag on the `/v1/models` response. It would have
   turned a design rewrite into a one-line check.

   We ended up with cross-model distillation instead — Ultra generates the
   labels, a Llama student learns them — which is arguably a better story. But we
   reached it by accident, not by design.

3. **A finished fine-tune is not a servable model.** The job yields downloadable
   checkpoints, and `fine_tuned_model` can be null even on success. We had
   written code that assumed the OpenAI semantics where the job hands back an id
   you can immediately pass as `model`. Documenting the gap between "succeeded"
   and "callable" prominently next to the job API would help.

4. **Empty completions.** Under concurrency we saw occasional `200` responses
   whose `choices[0].message.content` was empty with `finish_reason: "stop"`. It
   is not a rate limit and not an error, so a naive client treats it as a model
   that had nothing to say. In our case it silently collapsed test-vector
   generation and produced a *false pass* — the worst possible failure mode for a
   verification tool. We now treat an empty completion as retryable. If this is
   an expected condition, it deserves a named finish reason.

## NVIDIA Nemotron

**What worked well**

- Nemotron 3 Ultra handled the genuinely hard part of this domain: carrying
  fixed-point scale through a COBOL expression tree and deciding where
  quantisation happens. Several programs were byte-exact on the first
  translation, including one with sign overpunch and floating insertion
  pictures, which is the kind of formatting detail we expected to need repair.
- Given a failing input and a diff, it diagnosed root causes correctly rather
  than special-casing the failing case — we checked specifically for hard-coded
  expected outputs and did not find them.
- Nano produced well-formed JSON reliably for contract extraction, and its
  generated test vectors found real bugs that our deterministic PIC-derived
  boundary probes missed. The split was worth it.

**Observations worth passing to the model team**

1. **Ultra narrates its reasoning in plain prose, not in a delimited block.** On
   long prompts it would spend its entire output budget on analysis — "The user
   wants me to port a COBOL program. Let me analyze..." — and either never reach
   the code or get truncated mid-fence. There was no `<think>` wrapper to strip
   and no `reasoning_content` field populated, so the preamble is
   indistinguishable from the answer. Three mitigations were needed: a system
   prompt that forbids preamble outright, a 32k output budget, and falling back
   to a *shorter* prompt on retry. Prompt length correlated strongly with
   narration: the same repair task answered cleanly at ~2.7k prompt chars and
   essayed at roughly four times that.

   A reliable way to request "code only" — or consistently routing reasoning to
   `reasoning_content` — would remove a whole class of client-side fragility.

2. **Occasional response-shape drift on structured output.** Asked for a JSON
   object, Nano sometimes returned the bare array that should have been one of
   its fields. Cheap to normalise once you know, and it crashed one program's
   migration before we did.

3. First-pass translation quality was the single biggest lever on the end
   result, and it responded to *precision* in the prompt rather than volume.
   Two added rules about `ACCEPT` truncation direction took one program from
   32/34-after-three-repairs to 34/34-with-none.

## Nebius AI Cloud — Serverless AI Jobs

- Custom-container jobs were straightforward, and `--env-secret` backed by
  SecretStash is the right shape for passing an inference key into a batch job.
- **Jobs have no replica or parallelism flag.** We had designed a sharded sweep
  expecting something like `parallelism: 8`; a fan-out is instead N separate
  `nebius ai job create` calls with a shard index in the environment. That works
  fine and the shard partitioning is ours anyway, but "one job is one container
  run" is worth stating plainly in the jobs overview, since the surrounding
  language ("batch workloads", "data processing") suggests otherwise.
- The separation between the Token Factory key and Nebius AI Cloud CLI
  credentials is reasonable but it surprised us. A sentence in the Jobs docs
  noting that an inference key is not a cloud credential would help anyone
  wiring inference into a job.

## Summary

The platform's strongest feature for this project was the combination of an
unmodified OpenAI SDK with a queryable model list — that is what let one
codebase route work across three Nemotron tiers and measure the cost difference.
The two things that cost us most were both discoverability rather than
capability: a stale hostname still in circulation, and the fine-tunable catalog
being separate from the served catalog.
